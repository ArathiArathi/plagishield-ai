## What the Platform Does

- **Plagiarism detection** — similarity scoring with source matches and snippets.
- **AI-content detection** — probability that content was generated by an LLM, with confidence and reasoning.
- **Grammar & style** — severity-graded issues with suggested fixes.
- **Citation verification** — APA / MLA / IEEE format and completeness checks.
- **Document management** — drag-and-drop upload, versioned history, signed downloads.
- **Reports & analytics** — quality radar, distribution charts, submission trends.
- **Institutional repository** — indexed prior submissions for cross-checking.
- **Team & subscription** — role-aware seats and tiered plans.

## Data Model

| Table | Purpose | Key columns |
| --- | --- | --- |
| `profiles` | Public user profile | `id`, `first_name`, `last_name`, `institution` |
| `user_roles` | RBAC mapping | `user_id`, `role` (enum) |
| `documents` | Document record | `owner_id`, `name`, `status`, `latest_version` |
| `document_versions` | Each upload revision | `document_id`, `version`, `storage_path` |
| `analyses` | Per-version results | `similarity_score`, `ai_score`, `grammar_score`, `citation_score`, `results` (jsonb) |

Storage bucket: **`documents`** (private). Path pattern: `{user_id}/{document_id}/v{n}-{timestamp}-{filename}`.

## Roles & Route Access

Roles: `student`, `faculty`, `institution_admin`, `super_admin`.

| Route | Allowed roles |
| --- | --- |
| `/`, `/documents`, `/analysis`, `/reports`, `/settings` | all roles |
| `/analytics`, `/repository` | faculty, institution_admin, super_admin |
| `/team`, `/subscription` | institution_admin, super_admin |

Enforced by `RoleGuard` in `src/routes/__root.tsx` and by sidebar visibility in `AppSidebar.tsx`. Database access is independently enforced by Supabase RLS using the `has_role()` security-definer function.

## Analysis Workflow

1. User drops a file on `/documents`.
2. Client creates a `documents` row (or bumps version for existing doc).
3. File uploaded to Storage at `{uid}/{docId}/v{n}-…`.
4. Client inserts a `document_versions` row + a pending `analyses` row.
5. Client calls the `runAnalysis` server function (`src/lib/analysis.functions.ts`).
6. Server downloads via `supabaseAdmin`, extracts text, sends an excerpt to the Lovable AI Gateway (Gemini 2.5 Flash, JSON response).
7. Server writes back the four scores + structured `results` JSON, marks document `analyzed`.
8. UI invalidates queries; new scores appear in the table.

## Local Setup (outside Lovable)

Prereqs: Node 20+, Bun (or npm), a Supabase project.

```bash
git clone <repo-url> plagishield-ai
cd plagishield-ai
bun install   # or: npm install
```

Create `.env`:

```bash
VITE_SUPABASE_URL="https://<ref>.supabase.co"
VITE_SUPABASE_PUBLISHABLE_KEY="<anon publishable key>"
VITE_SUPABASE_PROJECT_ID="<project-id>"
# Server-only:
SUPABASE_URL="https://<ref>.supabase.co"
SUPABASE_PUBLISHABLE_KEY="<anon key>"
SUPABASE_SERVICE_ROLE_KEY="<service role>"
LOVABLE_API_KEY="<lovable ai gateway key>"
```

Apply migrations:

```bash
# Using Supabase CLI
supabase link --project-ref <ref>
supabase db push
```

Create the storage bucket (Supabase Dashboard → Storage → New bucket → name `documents`, private). The bucket RLS policies are included in the migrations.

Enable Google OAuth in Supabase Auth → Providers → Google.

Run:

```bash
bun dev    # http://localhost:5173
bun run build
bun start
```

## Sign-up & Roles in Practice

- New users sign up via `/register` and pick **Student** or **Faculty**. `institution_admin` is also self-selectable; `super_admin` cannot be self-assigned (the `handle_new_user()` trigger downgrades any elevated claim).
- A super admin must promote users by inserting into `public.user_roles` directly (only super admins have the policy to do so).
